# 테스트 명세서

## TS-001 인증 및 권한 관리 시나리오 (Security & Gateway)

모든 시스템 접근 요청에 대해 보안 정책(인증/인가)이 적절하게 적용되는지 검증한다.

### TC-001-001: JWT 유효성 검사 실패 테스트

만료되었거나 서명이 잘못된 Access Token 을 포함하여 모든 핵심 API (예: 계좌 조회) 에 접근을 시도한다.

- [ ] API Gateway 단계에서 401 Unauthorized 응답 코드를 반환하는가
- [ ] 상세 오류 메시지에 권한 문제임을 명시하는가

> Access Token의 유효성은 검증하지만 테스트를 편하게 하기 위해서 인증 여부는 확인하지 않도록 구현했습니다. 인증(Authentication)은 프로덕션 환경에서는 보안과 관련된 중요한 문제이기 때문에 구현 후 테스트하겠습니다. 

### TC-001-002: 역할 기반 접근 통제 (RBAC) 테스트

일반 사용자 계정으로 관리자만 사용할 수 있는 API (예: 계좌 상태 강제 변경, 서비스 설정 변경) 에 접근을 시도한다.

- [ ] 403 Forbidden 응답 코드를 반환하는가
- [ ] 해당 요청이 비즈니스 로직에 도달하기 전에 차단되는가

> 관리자 전용 API를 만들지 않아서 테스트하지 못했습니다.

### TC-001-003: Gateway 라우팅 검증

외부에서 들어오는 트래픽이 오직 API Gateway 를 통해서만 접근 가능하며, 게이트웨이가 적절한 서비스로 요청을 분기(Route) 하는지 확인한다.

- [x] 잘못된 경로 요청 시 404 Not Found 가 반환되는가
- [x] 내부 마이크로서비스가 외부 노출되지 않는가

## TS-002 계좌 생명주기 관리 시나리오 (Account Lifecycle)

계좌 생성부터 폐쇄까지의 모든 상태 전이 로직과 비즈니스 규칙을 검증한다.

### TC-002-001: 정상적인 계좌 개설 흐름 테스트

필수 정보(성명, 비밀번호 등)를 입력하여 신규 계좌를 생성하고, 최초 조회 시 잔액 0과 ACTIVE 상태가 부여되는지 확인한다.

- [x] 성공 응답 코드 (201 Created)를 반환하는가
- [x] 데이터베이스에 정상적으로 레코드가 저장되었는가

### TC-002-002: 계좌 중복 생성 방지 테스트

동일한 고객 식별자(예: 주민등록번호 또는 휴대폰 번호)로 두 번째 계좌를 개설하려 할 때, 시스템이 이를 감지하고 트랜잭션을 실패시키는지 검증한다.

- [ ] 비즈니스 로직 레벨에서 오류가 발생하는가 
- [ ] `Unique Constraint Violation` 메시지와 함께 409 Conflict 에러를 반환하는가

### TC-002-003: 상태 전이 무결성 검증 (State Machine)

비활성화(INACTIVE) 상태의 계좌에 입금 또는 이체 시도를 하거나, 이미 폐쇄(CLOSED)된 계좌에서 거래를 시도할 때 시스템이 이를 차단하는지 확인한다.

- [ ] 해당 상태에서의 모든 트랜잭션 요청은 400 Bad Request 에러를 반환하는가

## TS-003 분산 트랜잭션 처리 시나리오 (Transaction & Consistency)

자금 이동 과정에서 발생하는 데이터 불일치 및 실패 상황을 안정적으로 복구하는지 검증한다.

### TC-003-001: 정상적인 입출금 흐름 테스트

잔액 50,000원이 있는 계좌 A 에서 20,000원 을 출금하여 트랜잭션을 완료시키고, Account Service 와 Transaction Service 의 잔액 및 거래 내역이 모두 정확히 일치하는지 확인한다.

- [x] 분산 트랜잭션 처리가 원자적으로(Atomically) 성공하는가
- [x] 모든 관련 서비스의 DB에 기록이 남는가

### TC-003-002: 자금 부족 및 롤백 테스트 (Fallback)

계좌 A 의 잔액보다 큰 금액을 출금 요청했을 때, 트랜잭션이 진행되지 않고 즉시 실패하는지 검증한다.

- [ ] 거래이력 자체가 만들어지지 않는가

### TC-003-003: 비동기 이체 및 보상 트랜잭션 검증 (Saga)

계좌 A 에서 계좌 B 로 이체를 시도할 때, 계좌 A 에서 잔액을 감소시키는데 성공했지만 계좌 B 에서 잔액을 증가시키는데 실패한 경우 보상 트랜젝션이 제대로 이루어지는지 확인한다.

- [ ] 시스템이 자동적으로 A의 잔액을 다시 원래대로 복구하는가

## TS-004 성능 및 안정성 시나리오 (Non-Functional Testing)

극한 상황(대규모 요청, 장애)에서도 서비스 연속성과 예측된 성능을 유지하는지 검증한다.

### TC-004-001: 동시성 부하 테스트 (Race Condition)

1초 동안 수백 명의 가상 사용자가 특정 계좌에 동시에 이체/출금 요청을 보내는 고부하 상황을 시뮬레이션한다.

- [ ] 데이터가 유실되거나 과도하게 차감되는 현상이 발생하지 않는가

### TC-004-002: 장애 주입 및 복구 테스트 (Chaos Engineering)

시스템 운영 중, 핵심 서비스 컨테이너 1개를 강제로 종료(KILL) 시키거나 네트워크 연결을 지연시키는 장애를 인위적으로 주입한다.

- [x] Circuit Breaker가 작동하는가
- [x] 필요한 경우 대체 응답이나 폴백 로직으로 작동하는가

> Transaction Service가 Account Service와 통신할 때 OpenFeign 클라이언트를 사용합니다. 게좌 잔액을 조회 후 입금/출금/이체 등의 거래를 진행하는데, 잔액 조회 단계에서 일정 횟수 이상 실패하면 Circuit Breaker가 작동하여 Account Service로의 통신이 일정 기간 차단됩니다.  
> Transaction Service에서 Notification Service로 Kafka를 통해서 메세지를 전달합니다. 마찬가지로 Circuit Breaker가 작동하여 일정 횟수 이상 통신에 실패하면 Kafka로의 메시지 전송이 차단됩니다.

### TC-004-003: 대용량 데이터 조회 성능 검증

1년 치의 모든 거래 내역 (수만 건) 을 특정 필터(예: 기간, 금액 범위)를 사용하여 검색했을 때, API 응답 시간이 정해진 SLA(Service Level Agreement) 기준을 만족하는지 측정한다.

- [ ] 페이지네이션과 최적화된 DB 쿼리를 통해 성능 저하 없이 데이터를 제공하는가
